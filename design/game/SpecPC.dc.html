统一接口 MGP v1 · 数据模型 · 权限模型

MGP（Momoko Game Protocol）是游戏服务端对 Momoko 暴露的一组 HTTP 接口。Momoko 只认这一份接口：页面上的玩家查询、GM 表单、卡池与活动编辑、玩家端自助功能，全部由服务端的 manifest 声明驱动。游戏差异留在服务端和适配器里，Momoko 前端不按游戏写死。

前缀 /mgp/v1，JSON，统一返回 { code, message, data, requestId }
方法路径作用学マス 服务端实现要点
{{r.m}} {{r.p}} {{r.what}} {{r.gk}}
签名鉴权 请求头 X-MGP-Key / Timestamp / Nonce / Signature；签名 = HMAC-SHA256(方法、路径、时间戳、随机数、body 摘要)。±5 分钟时间窗、拒绝重放——与现有节点 API Key 同一套方案，代码直接复用。托管模式下密钥由 Momoko 生成并写入服务端配置。
写操作约束 每个指令带 requestId 幂等；支持 dryRun 先预览变化；服务端提交成功后才返回成功，返回值列出实际变化（发了什么、扣了什么、剩余多少），Momoko 原样写进审计。
视图与表单不写死 views 声明玩家详情里有哪些分页（卡片网格 / 表格 / 键值），commands 的参数用 JSON Schema + x-picker 提示（奖励、偶像卡、道具…）。Momoko 按声明渲染；需要更讲究的展示时，再给该游戏加专属前端组件。

4 · 权限模型

{{k.t}} {{k.rule}} 例：{{k.ex}}
管理端：能进就能执行全部指令 沿用现有用户权限，只加一个权限项 game:gm（能否进入 GM 运营）。能进的管理员可以对任何服务器执行全部指令，不做按角色、按指令的授权。风险等级只决定交互：「高」要填原因，「危险」执行前自动备份；不做任何二次确认。
玩家端：自助开放 用户通行证跑在独立 server（默认 :22634，主后台是 :22633），只注册玩家路由，和后台不共享会话与令牌。每台服务器、每条指令一行：是否开放给玩家、每天次数、间隔、是否需要管理员审批、玩家看到的说明。目标固定为「自己绑定的那个游戏账号」。服务端在 manifest 里先声明哪些指令「允许自助」，Momoko 只能在这个范围内开放。玩家执行同样进 GM 记录，标「玩家自助」。

6 · 游戏素材：当前端资源管理，不走游戏服务端

MGP 只返回 ID（卡 ID、卡池 ID、道具 ID…），图片全部由前端自带
1从哪里拿 学マス客户端资源目录 resource/：manifest.json 记录资源名与 md5，文件在 blobs/<md5 前 2 位>/<md5>。每个文件前 256 字节按资源名用 resource_codec.name_mask(name) 还原，再用 UnityPy 读 UnityFS（FALLBACK_UNITY_VERSION = "2022.3.21f1"），导出 Texture2D。
2离线导出 脚本 frontend/scripts/games/gakumas/extract-assets.py：按一份资源名前缀清单只导出界面用得到的几类，转 WebP（质量 82），超过上限才缩小、不放大，输出到 frontend/src/games/gakumas/assets/，同时生成 manifest.ts（游戏资源 ID → 文件）。游戏更新后重新跑一次再提交；文件多了就用 Git LFS。
3前端怎么用 页面拿到游戏数据里的 ID，调用 gameAsset('gakumas', id) 查 manifest；文件用 import.meta.glob(..., { query: '?url' }) 按需加载，Vite 打包带 hash、可长期缓存，随前端一起嵌进 Momoko 二进制。用户通行证 server 用同一份构建。查不到的 ID 显示占位图，不去请求游戏服务端。
